# 成都慢游 · 新手引导演示剧本

> 与当前原型同步的演示脚本。剧情、动作、文案和节奏以这里的约定为准。

## 一、这段引导要讲什么

用一篇逐渐成形的成都游记，带观众走过“开始写作 → 整理结构 → 丰富表达 → 展示与分享”。始终围绕同一份文档展开，让每项功能都有具体用途。

用户负责观看和决定何时继续，演示中的点击、输入、切换和拖动由程序完成。

### 已明确的播放节奏

- 采用“关键节点点击继续”：卡片先高亮当前目标并说明下一步，用户点击“继续”后，程序才执行该节点；动作完成后再次停住，等待用户看清结果。
- 连续输入、滚动和拖动仍由程序自动完成，不按每个字符或每一帧要求用户确认；只有切换模式、进入下一视角、打开菜单、看清结果等自然节点需要点击。
- “继续”只控制演示动作，不会误触真实工作区；演示中的自动点击和输入仍走演示会话，不写入用户文件。

- 刚进入时显示遮罩说明，点击“开始吧”才播放；等待期间保留用户原来的界面。
- 第一幕直接进入空白演示文档，不再演示“文件 → 新建”。
- 进入空白正文后，先高亮正文区并说明“在这里写下游记”，用户点击“继续”后立即开始逐字输入。
- 第一幕的标题与段落连续写完，中间不插入讲解停顿；写完后停住展示成果，点击“继续”进入第二幕开场卡。
- 每幕演示结束后直接进入下一幕的开场卡，不再插入单独的幕间说明卡；从第二幕起，开场卡带“上一步”。最后一幕结束后才显示最终成果卡。
- 每张需要操作的卡片在按钮区中央显示步数 **x / 9**：开场为 1/9，八个幕依次为 2/9–9/9，让用户随时知道进行到第几步。
- 播放时最多显示一行轻提示；需要说明关键切换时，再显示一张短提示卡，避免遮住正在发生的操作。
- 每个关键节点完成后，卡片按钮显示“继续”，由用户点击后才进入下一节点；停驻卡均提供“跳过本段”与“上一步”（开场除外）。
- 动作本身（打字、切换、拖动、菜单展开）播完即止；关键节点由用户点击“继续”后执行，不使用固定倒计时。需要阅读结果时保持停住，直到用户继续。
- 逐字输入分两档速度：短句约 **30 毫秒/字**，大段补充约 **8–10 毫秒/字**；单幕输入时间合计不超过 **8 秒**，全片自动播放合计约 **2–3 分钟**（不含卡片停留）。
- 卡片不设倒计时，可以一直看；支持上一步、跳过和退出。

### 遮罩说明

- 遮罩覆盖应用工作区并压暗背景，只把当前演示区域挖空高亮；高亮位置跟随真实控件，不使用漂移的静态示意图。
- 播放期间分三档呈现，避免大对话框挡住动作：
  1. **仅高亮**：连续输入、滚动等不需要解说的动作，只保留挖空与演示鼠标。
  2. **轻提示**：大多数动作配一行文字（即各幕镜头表中的“简短提示”），无标题、无按钮，贴在高亮边缘或工作区底部居中，以不遮挡动作和输入位置为准，动作结束即隐藏。
  3. **短提示卡**：仅用于关键切换（源码/即时切换、进入演示、打开菜单），带标题与一句话；动作完成后收起。
- 提示卡不放置勾选图标、完成状态或重复的幕标题；卡片只保留标题、一个简短说明和必要的操作按钮。
- 说明卡停靠在工作区一侧的空白处，不遮挡本幕成果；只有第八幕的最终成果卡可以居中。
- 键盘与无障碍：Esc 随时退出，Tab 在卡片按钮间移动；轻提示与卡片文字对读屏走实时区域；系统开启“减少动画”时压缩卡片与光标过渡，逐字输入保留。

### 贯穿全片的画面规则

1. 文档从空白开始，新增文字要有输入过程，结构变化要有对应操作。
2. 同一幕只突出一个主要收获。鼠标、高亮和提示一起指向当前动作。
3. 提示框避开输入位置、菜单项和图表主体，打字时不随每个字符跳动。
4. 同一份游记贯穿八幕；正常播放时，前一幕的成果就是后一幕的起点。
5. 每一幕从本幕开始前恢复；返回上一步也不重复叠加内容。
6. 跳过时恢复本幕起点，再准备下一幕需要的内容。
7. 退出或完成后回到进入引导前的文档与界面；演示内容不保存到用户文件，不实际下载或复制。

## 三、开场：先看看，怎么使用

**画面**：原界面上覆盖遮罩，中间显示说明对话框。此时不切换文档、不打开菜单、不开始输入。

**对话框文案**：

> **快速上手** · 1/9
>
> 运行软件即可立即创作哟，跟着演示看一遍核心功能。
>
> **开始吧**

右上角提供关闭入口。用户点击“开始吧”后，说明对话框收起，开始第一幕。

首次进入工作区时自动弹出这个说明；看过一次后不再自动弹出（记入本地偏好），之后可从工具栏的“快速上手”入口重新进入。退出或跳过都不影响用户自己的文档。

## 四、第一幕：即时模式

**本幕收获**：看到一篇空白文档如何直接开始写作。

| 镜头 | 画面与自动动作 | 简短提示 | 节奏 |
| --- | --- | --- | --- |
| 1 | 进入空白演示文档，内容区挖空高亮并显示引导卡 | 在这里写下游记。 | 等待用户点击“继续” |
| 2 | 在正文中逐字输入一级标题“成都，慢慢走” | 写下这趟旅行的标题。 | 按正常打字节奏连续输入 |
| 3 | 换行，逐字输入第一段游记 | 内容会即时呈现。 | 紧接标题，不等待 |
| 4 | 输入结束，提示“内容已经写下，先读一遍刚才的结果。”，移走演示鼠标，展示刚写好的内容 | 内容已经写下，先读一遍刚才的结果。 | 等待用户点击“继续”后进入第二幕开场卡 |

**这一幕实际写出的内容**：

```markdown
# 成都，慢慢走

这个周末，去成都。把脚步放慢一点，给茶香和街巷多留些时间。
```

正文采用即时编辑效果，标题和段落在输入过程中成形。标题与首段共约 45 字，按约 30 毫秒/字逐字输入、一气呵成；这一速度也是全片短句输入的基准。

第一幕停驻卡显示 **2/9**；点击“继续”后直接进入第二幕开场卡，不再弹出单独的幕间说明卡。

## 五、第二幕：两种写法

**起点**：第一幕刚写好的标题和段落，不额外预填文章。

| 镜头 | 画面与自动动作 | 简短提示 | 观看时间 |
| --- | --- | --- | --- |
| 1 | 高亮左下角“切换源码模式”，显示第二幕开场卡 | 支持源码或即时渲染编辑，点击下面的切换按钮方便切换。 | 等待用户点击“继续”后切换 |
| 2 | 在源码中定位标题和段落，逐字改写第一段 | 在源码里，也能继续修改。 | 输入后短暂停留 |
| 3 | 在文末逐字补充出发清单和两天行程 | 加一份清单，再把行程写下来。 | 连续输入，不在每行之间等待 |
| 4 | 再次高亮“切换源码模式”，显示引导卡，等待点击后切换 | 再次点击，切换源码模式哦。 | 等待用户点击“继续”后切换 |
| 5 | 回到即时渲染，在正文末尾再输入“沿着这条路线，慢慢走。” | 切回即时渲染，继续直接写一段。 | 输入结束后等待用户点击“继续”进入第三幕开场卡 |

**本幕新增文段**：

```markdown
## 出发清单

- [ ] 带上相机
- [ ] 预订车票

## 第一天行程

### 人民公园

坐在茶社里，喝一碗盖碗茶。

### 宽窄巷子

沿着青砖小巷，看看老院子。

## 第二天行程

### 熊猫基地

早一点出发，去看大熊猫。

## 锦里夜游

等灯笼亮起来，再去锦里走走。

### 旅途随手记

记下今天最喜欢的一碗茶和一条巷子。

沿着这条路线，慢慢走。
```

结尾句“沿着这条路线，慢慢走。”是第二幕的收尾，也是文档的一部分：第三幕及之后的起点都包含它，跳过、回看或撤销时都不得让它悄悄消失。

（可选微镜头，待评审）切回即时渲染后，先点击“预订车票”的勾选框展示任务清单可以交互，再逐字输入结尾句；若保留，后续各幕基线中该清单项同步置为已勾选。

第二幕开场卡显示 **3/9** 并带“上一步”，可返回第一幕重看。

## 六、第三幕：大纲与导图

**起点**：第二幕写好的完整游记（含结尾句“沿着这条路线，慢慢走。”）。

| 镜头 | 画面与自动动作 | 简短提示 | 观看时间 |

| 2 | 大纲展开，点击“第一天行程”，正文定位到该章节 | 大纲会列出标题，点击“第一天行程”定位内容。 | 等待用户点击“继续”后定位 |
| 3 | 高亮中间“导图”Tab 并点击切换 | 点击“导图”，查看全局结构。 | 等待用户点击“继续”后切换 |
| 4 | 导图画布挖空高亮 | 导图把标题关系画在这里。 | 等待用户点击“继续” |
| 5 | 将“锦里夜游”拖到“第一天行程”下，正文与子章节一起移动 | 把锦里夜游安排到第一天晚上。 | 等待用户点击“继续”后移动 |
| 6 | 停留在导图上，看清层级随移动更新 | 章节和下面的随手记，一起移动了。 | 等待用户点击“继续” |

拖动时让观众看清起点、移动路径和落点；移动后，“锦里夜游”的正文及“旅途随手记”跟随章节一起移动。移动与撤销都停留在导图上完成。

## 九、第六幕：Mermaid 图表

**本幕主角**：一张真正由文字生成、还能继续修改的 Mermaid 流程图。

| 镜头 | 画面与自动动作 | 简短提示 | 观看时间 |
| --- | --- | --- | --- |
| 1 | 定位文末，在源码布局中逐字输入小节标题；图表代码不逐字展示半成品，在标题后一次性补全完整的 Mermaid 代码块 | 把几个想去的地方，连成一条路线。 | 连续输入 |
| 2 | 代码块补全后切换到“源码 + 渲染”对照布局，展示渲染后的路线图 | 一段文字，变成了清楚的路线。 | 等待用户点击“继续” |
| 3 | 在对照布局中定位图表源码，将“宽窄巷子”改为“宽窄巷子 · 喝茶漫步” | 给这一站，补上想做的事情。 | 点击继续后自动修改 |
| 4 | 展示更新后的图，突出发生变化的节点 | 图里的这一站，也跟着更新了。 | 等待用户点击“继续”进入下一幕开场卡 |

**本幕输入的图表内容**：

````markdown
## 成都慢游路线

```mermaid
flowchart LR
  A[人民公园] --> B[宽窄巷子]
  B --> C[锦里夜游]
```
````

图表应在完整代码输入后展示成图，不把未写完时的错误提示当成演示内容；小节标题逐字输入、代码块整体落纸就是为了这一点。修改节点时源码与图并排可见，展示同一张图的更新结果。

**下一幕说明卡**：

> **演示模式**
>
> 从正文切到导图，按章节讲解。

**可选加场，待评审决定**：如果希望再丰富一点，可以增加一张“两天行程”的甘特图，突出时间安排；也可以把“输入代码”改为从工具栏的图表库插入流程图模板。建议主线先保留手写源码这一张路线图，第二种方式作为可选内容，控制全片长度。

## 十一、第八幕：保存与分享

**起点**：回到完整游记的阅读视图。

| 镜头 | 画面与自动动作 | 简短提示 | 观看时间 |

| 3 | 切到工具菜单，展示适合发布平台的复制入口 | 准备发布时，从这里选择对应的平台。 | 等待用户点击“继续” |
| 4 | 收起菜单，展示完整游记与最终成果卡 | 不再显示动作提示 | 等待用户点击“开始自己的写作” |

本幕只展示入口与用途，不实际保存、下载、打开外站或写入剪贴板。手机与窄窗口从底部工具菜单的真实入口打开，停留时间相同。

**最终成果卡**：

> **保存与分享**
>
> 保存、导出或分享作品。

点击主按钮后结束引导，恢复进入前的文档与界面。

## 十二、不同屏幕怎样讲同一个故事

| 屏幕 | 表达方式 |
| --- | --- |
| 桌面 | 需要比较时并排展示源码、正文和导图，保持对应内容在可见范围内。 |
| 平板 | 优先使用双栏对照；三种视角分两次展示，不把三栏挤在一起。 |
| 手机 | 按“源码 → 正文 → 导图”的顺序切换，每次只突出一个结果；第一幕直接进入空白演示文档。 |

各端共用同一篇成都游记、同一组成果和观看顺序；菜单名称与点击位置按各端真实入口处理。触屏端轻提示与成果卡靠底部全宽摆放；播放中途调整窗口或旋转屏幕时，当前幕继续，高亮与卡片即时重排。

## 十三、本稿的评审重点

1. **先看开场与第一幕**：首次进入是否自动弹出说明；说明是否足够短；约 30 毫秒/字的打字节奏观众是否跟得上。
2. **再看每幕只讲什么**：第二幕新增行程的文字量、可选的“勾选预订车票”微镜头，以及第三幕“大纲、导图、移动、撤销”是否需要进一步精简。
3. **确认提示的呈现方式**：轻提示与短提示卡的界限是否清楚；成果卡停靠一侧后，是否仍能同时看到“刚才做了什么”和“得到了什么”。
4. **确认图表的分量**：主线只放路线流程图，还是再加一张可选的行程甘特图；是否改用图表库插入的方式呈现。
5. **最后确认成果文案**：每幕完成后，用户是否能用一句话说出自己刚看懂了什么。

## 十四、附：与当前实现的已知差异

剧本是唯一约定：改动先落在本稿，再同步原型（`design/assets/desktop/guide.js`）与应用（`apps/vex` 的 `WorkspaceGuide` 及引导编排）。原型已按本稿实现步数计数、开场卡“上一步”、真实大纲/导图 Tab 点击与样式自动轮播；以下只保留验收时需要留意的边界：

| 端 | 差异 | 处理 |
| --- | --- | --- |
| 应用 | 步数计数（x/9）、停驻卡“上一步”、幕间说明卡取消尚未同步 | 按本稿同步卡片结构与计数 |
| 应用 | 第三幕尚未点击真实“大纲”“导图”Tab；第四、五幕尚未自动轮播样式 | 按本稿镜头表同步动作顺序 |
| 应用 | 演示输入通过会话替换逐字呈现，和原型的 DOM 输入动画实现不同 | 以可见节奏和最终文档结果为验收标准 |
| 原型与应用 | 关键节点都由“继续”按钮放行，连续输入仍自动完成 | 验收时重点确认未点击“继续”前不会切换、输入或进入下一节点 |
| 应用 | 手机端菜单使用底部触控菜单，桌面端使用标题栏菜单 | 两端保持相同的入口语义和停留节奏 |
| 应用 | 演示卡片和轻提示由 Flutter 布局测量，窗口缩放时位置可能与原型有少量像素差 | 以高亮目标不被遮挡、提示贴近目标为验收标准 |

## 十五、平台兼容性记录

- 在 Windows Server 及其他较旧的 Windows 操作系统上，软件窗体标题栏上方的边框可能不显示；较新的 Windows 版本显示正常。
- 应用端在自绘标题栏增加顶部边框作为旧系统回退线；原生标题栏隐藏逻辑仍由 `window_manager` 管理。Windows Server/旧 Windows 仍需在目标系统安装包上做一次目视确认。

## 十六、Markdown 功能演示与界面约定

以下内容属于正文编辑、即时渲染和阅读视图的共同能力，原型样例 `design/assets/desktop/samples.js` 中提供了可直接验收的《Markdown 功能示例.md》：

| 功能 | 交互与呈现 |
| --- | --- |
| 列表层级 | 在 `-` 前使用空格即可形成子列表；即时编辑、阅读和导出保留层级关系。 |
| `[TOC]` | 单独一行时显示可点击目录；点击目录项定位到对应标题。 |
| 表格 | 没有显式 `:` 对齐标记时，表头与所有列默认左对齐；显式左、中、右标记仍按原写法生效。 |
| 脚注 | `[^1]` 在正文显示为可点击引用，文末 `[^1]: ...` 显示脚注内容，并提供返回正文入口。 |
| Callout | `> [!INFO]` 显示信息提示框，`> [!WARNING]` 显示警告提示框；提示框保留正文可读性，不阻断编辑。 |

这些能力的演示不加入新手引导主线，避免打断“写作—结构—分享”的核心路径；用户可从样例文档或自己的 Markdown 直接验证。目录、脚注的点击定位遵循现有大纲定位反馈，滚动到目标后保留短暂高亮。

## 十七、已记录但待原型验收的界面需求

- 正文内容区宽度参考 Typora：阅读与即时编辑视图取消居中栏宽限制（原 1280/780px），正文随内容区铺满，仅保留约 48px 内边距；演示模式的全屏排版保持原有栏宽。原型已改，待应用同步。
- 左侧栏与中间文档区之间的拖动，分隔边界应跟随鼠标实时移动，并记住拖动后的宽度；问题重点是拖动反馈滞后，不只是扩大命中区域。
- 文件树或文件列表节点右键提供“在新窗口打开”与“打开文件位置”：文件在新进程打开，文件夹在新进程进入打开文件夹流程；“打开文件位置”调用系统文件管理器并定位到该节点。
- Windows Server 等旧 Windows 上补齐窗体标题栏上方边框，高版本 Windows 保持原有窗口效果。
