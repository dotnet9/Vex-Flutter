## 3. 先记住这十个词

| 名词 | 小白版解释 | 在 Vex 中的例子 |
| --- | --- | --- |
| Dart | 写程序使用的语言 | `.dart` 源文件 |
| Flutter | 用 Dart 构建界面的框架和工具 | 编辑区、对话框、导图界面 |
| SDK | 开发工具箱 | `flutter`、`dart` 命令及其运行依赖 |
| Widget | 一个界面描述单元 | 文本、按钮、整页工作区 |
| State | 当前记住的信息 | 当前文档、主题、选区 |
| Controller | 让外部控制某个组件的对象 | 编辑器控制器、导图控制器 |
| ViewModel | 协调界面状态和业务动作的对象 | 打开文件、保存、改变布局 |
| Repository | 统一封装数据存取的接口 | 设置仓库、恢复草稿仓库 |
| Package | 可以被其他代码引用的一组能力 | `vex_editor` |
| Build | 把源码变成可运行程序 | `flutter build windows --release` |

不要一开始就背缩写。第一次看不懂是正常的，遇到它时回来查即可。

## 4. 三种“文档”有什么区别

1. **需求文档**：说清楚“用户需要什么、怎么验收”。例如自动保存默认关闭。
2. **设计文档**：说清楚“由哪些模块、通过什么数据流实现”。例如文件服务负责写磁盘，界面不直接操作文件。
3. **用户 Markdown**：使用软件编辑的内容。例如这篇文章。它不是项目代码，也不自动加入软件安装包。

本套需求、设计文档是对当前实现和已确认产品方向的梳理，不是从零虚构的未来架构。

## 6. 学习时的三个边界

> **测试通过，不等于所有设备没有问题。** 模拟手机尺寸不能替代真实手机；Windows 运行成功不能替代 macOS 验收。

> **恢复草稿，不等于版本备份。** 真正重要的内容仍要保存到 `.md`，并备份整个笔记和附件目录。

> **被 Git 忽略，不等于可以删除。** `build` 可以重建；`.signing` 里的发行密钥不可随意重建或丢失。

本套文档与配图 `docs/assets` 已纳入源码仓库，**提交并推送后，换电脑克隆仓库即可取得**。尚未提交的练习修改仍需提交或单独备份；用户笔记、配置和签名材料不会因此自动进入 Git。
